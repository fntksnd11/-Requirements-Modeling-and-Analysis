# ADR-0001: Вибір Activity-діаграми (Mermaid `flowchart TD`) для опису бізнес-процесу

- **Статус:** Прийнято
- **Дата:** 2026-11-25
- **Контекст:** У межах Лабораторної роботи №4 необхідно описати один цілісний бізнес-процес як розвиток прецеденту (UC) із Завдання 2 та забезпечити наскрізну узгодженість із моделями взаємодії з Лабораторної роботи №3 (`lab3/model_main.md`, `lab3/model_declined.md`, `lab3/model_alt.md`). Обов'язковими умовами є використання однієї точної форми без змішування нотацій, наявність початку та завершальних станів, умовного розгалуження (`if/else`), паралельних гілок (`fork`/`join`), надсилання повідомлення іншому учаснику та чітко показаної реакції на підтвердження, відмову й відсутність відповіді (таймаут / альтернативна гілка).

## Критерії оцінювання варіантів
1. **Точність передачі потоку керування та паралелізму:** здатність наочно показати послідовність кроків, паралельну обробку (`fork` -> гілки -> `join`) та умовні переходи в межах одного процесу.
2. **Відображення повідомлень і реакцій (у т.ч. мовчання / таймауту):** можливість чітко показати відправника, отримувача, розгалуження за відповіддю та перехід при відсутності відповіді.
3. **Узгодженість із попередніми моделями:** зручність зіставлення з діаграмами послідовності з Лаби 3 (`main`, `declined`, `alt`) та збереження єдиного наскрізного ланцюга моделей.
4. **Зручність рев'ю та версіонування у Git:** читабельність у текстовому `diff`, простота внесення точкових правок і генерації рендеру без зайвих артефактів.

## Розглянуті альтернативи

### Варіант 1: Activity-діаграма (Mermaid `flowchart TD`)
- **Опис:** декларативний текстовий опис потоку дій, керуючих вузлів синхронізації, розгалужень і взаємодії між ролями з рендером у векторне зображення.
- **Переваги:**
  - наочно показує потік керування, паралельні гілки (`fork`/`join`) і переходи за умовами чи таймаутом;
  - зберігається у звичайному Markdown/тексті, тому зміни добре видно у Git diff та легко пов'язувати з комітами і специфікацією;
  - швидко оновлюється під час ітерацій та рендериться в один файл (`render.svg`).
- **Недоліки:**
  - не має вбудованої формальної XML-схеми BPMN 2.0 для промислових оркестраторів;
  - за потреби великої кількості вкладених дорожок (`swimlanes`) потребує акуратного найменування вузлів, щоб схема залишалася читабельною.

### Варіант 2: BPMN 2.0 XML (`bpmn.io` / Camunda Modeler)
- **Опис:** формалізована діаграма бізнес-процесу у стандарті BPMN 2.0 із пулами, подіями та потоками повідомлень.
- **Переваги:**
  - сильний стандарт для опису міжсистемної інтеграції, таймерів і подій повідомлень у промислових системах;
  - чітко розмежовує учасників через пули та `message flow`.
- **Недоліки:**
  - XML-представлення громіздке, погано читається у Git diff під час рев'ю і створює багато службових змін координат при дрібних правках;
  - вимагає додаткових інструментів для візуальної перевірки та не дає переваг перед Activity-діаграмою для навчального рев'ю за ~5 хвилин.

### Варіант 3: Машина станів (`Mermaid stateDiagram-v2`)
- **Опис:** модель переходів між станами процесу/сутності під дією подій і умов.
- **Переваги:**
  - добре підходить для опису життєвого циклу одного об'єкта або транзакції та його станів;
  - підтримується безпосередньо в Mermaid.
- **Недоліки:**
  - менш наочно передає покрокову міжрольову взаємодію та паралельне виконання кількох дій (`fork`/`join`) у рамках єдиного потоку процесу;
  - акцентує увагу на станах, тоді як мета цього завдання — описати саме потік дій, розгалужень, синхронізації та повідомлень процесу.

## Прийняте рішення
Обрано **Варіант 1 — Activity-діаграму (Mermaid `flowchart TD`)**.
Вона найкраще поєднує наочність потоку керування, підтримку паралельних гілок і розгалужень, відображення обміну повідомленнями з реакцією на відповідь або її відсутність та зручність перевірки змін у репозиторії.

## Наслідки та компроміси
- **Позитивні наслідки:**
  - прозорий текстовий diff у `lab4/model.md` при кожній ітерації правок після оновлення `lab4/spec.md`;
  - пряме зіставлення гілок процесу зі сценаріями `main`, `declined` і `alt` з Лаби 3;
  - один чистий рендер (`lab4/render.svg`) без дублюючих файлів.
- **Компроміси / обмеження:**
  - відмовилися від формального BPMN 2.0 XML на користь читабельності у Git та швидкості рев'ю;
  - замість фокусу на станах однієї сутності (`stateDiagram-v2`) зроблено акцент на кроках процесу, синхронізації та реакції на події/таймаут.
